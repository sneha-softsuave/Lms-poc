# .claude/ — a portable Claude Code workspace

A multi-agent pipeline for **any task on an existing codebase** — fix a bug, add a
feature, refactor, write missing tests, chase a slowdown, do an upgrade, or just
investigate a question. It takes the task from shaping through planning,
implementation, criticism, verification, and code review, and ends with a
ready-to-run commit and PR block.

**Stack-agnostic.** Nothing here names a language, framework, or business domain.
Everything project-specific lives in one generated file, `.claude/stack-profile.md`.
The same folder installs into a TypeScript service, a Python CLI, or a Go library.

**It never touches git.** No branch, no commit, no push, no PR. That is enforced by
`permissions.deny` in `settings.json`, not left to the agent's judgement.

## Install

```bash
cp -r .claude /path/to/your-project/
cd /path/to/your-project

cat >> .gitignore <<'EOF'
.claude/settings.local.json
.gitnexus/
SQUAD_PLAN_*.md
SQUAD_DELIVERY_*.md
EOF
```

Then open the project in Claude Code and say:

```
squad setup
```

That detects your stack, resolves your real lint/test/build commands, indexes the
code graph, and writes `stack-profile.md`. Restart Claude Code once afterwards so
the graph's MCP server picks up the new index.

Requires Node.js (for the graph indexer) and bash (for the lint hook — on Windows
that comes with Git for Windows).

## Use

```
squad up the settings page returns 500 when the org has no billing contact
squad up add CSV export to the reports endpoint
squad up write tests for the notification service
squad up the ticket list is slow once a tenant has 10k rows
squad up rename OrderService to FulfilmentService everywhere
squad up why do we call the settings API twice on page load?
squad up ULTIMATE migrate session storage to the new backend
```

Same pipeline every time. What changes is the prep it does first (Phase 0.5):
a bug goes to `bug-triager` for the root cause; a feature goes to `code-explorer`
to find where it plugs in and what conventions to match; a refactor starts from
graph impact, because there the blast radius *is* the risk; a performance task must
take a before-measurement or it cannot prove it helped. An investigation can end
with findings and no code change at all — that is a valid outcome, not a failure.

For ad-hoc questions, just ask; `deep-codebase-explorer` picks how much machinery
the question warrants. `/squad-architect [task]` recommends a shape without running
anything.

## Layout

```
.claude/
├── settings.json        # deny-list for git/remote writes; the lint hook
├── stack-profile.md     # GENERATED by squad setup — the only project-specific file
├── agents/              # 7 subagents, each with locked-down tools
├── commands/            # /squad-architect
├── hooks/               # lint-changed.sh — runs YOUR lint command on changed files
└── skills/
    ├── squad-up/                 # the pipeline
    ├── deep-codebase-explorer/   # question router
    ├── squad-setup/              # this installer
    └── fable-rigor/              # the evidence contract every agent reads first
```

`skills/gitnexus/` is **not** shipped here on purpose — `gitnexus analyze` installs
its own copies during setup, matched to the version you actually have, and
regenerates them on every run. Shipping our own would pin stale tool signatures
and be silently overwritten anyway.

## The agents

| Agent | Role | Why it's separate |
|---|---|---|
| `bug-triager` | Locates the root cause | Read-only. Cannot "just quickly fix it" and skip the plan. |
| `code-explorer` | Traces how something works | Read-only, no Bash. |
| `squad-planner` | Writes the plan | Cannot edit source. Plans only. |
| `squad-implementer` | Builds one lane | Reports raw evidence; forbidden from grading itself. |
| `squad-critic` | Quality and intent | No Bash — judges, never runs. |
| `squad-verifier` | Re-runs every claim | Cannot edit. Unreproduced evidence is treated as false. |
| `squad-code-reviewer` | Final adversarial review | Applies the safety lens matching your project type. |

The separation is the point: **the agent that produced an artifact never grades it.**
Three independent phases check the work, and the verifier re-runs commands itself
rather than trusting pasted output.

Every agent reads `skills/fable-rigor/SKILL.md` first — never cite a file you didn't
open, evidence or it didn't happen, report what you ran rather than a verdict.

## The two approval gates

`squad up` stops twice: once to approve the direction, once to approve the plan.
Nothing edits your code before the second yes. Beyond those, it runs to completion
and only interrupts to escalate a genuine failure (a lane failed twice, or the
8-loop cap was hit).

## Where the work comes out

- `SQUAD_PLAN_<slug>_<date>.md` — the plan, with a live execution trace (`squad resume` reads this)
- `SQUAD_DELIVERY_<slug>_<date>.md` — what changed, verification output, open items, and the commit/PR block you run

## The code graph

GitNexus indexes your code into a queryable call-graph, so "what breaks if I change
this" is answered by call edges rather than string matches. Grep finds the literal
references; the graph also finds the aliased re-export, the callback, the interface
dispatch — the difference between finding 3 call sites and finding 11.

Setup measures whether it can actually parse your language and records the answer
as `Graph support: full | partial | none`. Where support is `full`, the squad
refuses to plan without a live index. Where it is `none`, the pipeline runs anyway
and says so — a degraded check is fine, a silently degraded one is not.

Re-index cadence: once at squad start (the graph should reflect the code *before*
your change), and again after implementation so the reviewer sees new symbols.
In between, `detect_changes` maps working-tree edits onto the existing graph.

## Customising

- **Personal overrides** → `.claude/settings.local.json` (gitignored). Never the team file.
- **Ticket-system rules** — if you want Jira/Linear/Notion writes to prompt rather than
  proceed, add those MCP tool names to a `permissions.ask` array in `settings.json`.
  None ship by default; tool names differ per connector, so copy the exact name from
  your session rather than guessing.
- **Project-specific agents** → drop a new `.md` into `agents/`; the planner will
  assign it if the plan names it.

Everything else that varies between projects belongs in `stack-profile.md`. If a
second project ever needs an agent file edited, that fact belongs in the profile
instead — that is the test of whether this stayed portable.

## Measured behaviour (gitnexus 1.6.9, verified 2026-07-23)

Established by running it against a real polyglot repo, not from docs:

- **`analyze` appends to `CLAUDE.md` / `AGENTS.md`, it does not overwrite.** It writes
  a block fenced by `<!-- gitnexus:start -->` … `<!-- gitnexus:end -->` and rewrites
  only that block on re-runs. Surrounding content is untouched, byte for byte. Setup
  still takes a backup first — cheap, and it is what proved this.
- **`analyze` overwrites everything in `.claude/skills/gitnexus/`** with its own
  current copies. Do not hand-edit those files; edits are reverted on the next run.
- **Index lives in `.gitnexus/`** in the repo root, with a global registry at
  `~/.gitnexus/registry.json`. It adds `.gitnexus/` to `.git/info/exclude` itself,
  so no `.gitignore` change is needed for it.
- **Languages:** indexed Python and TypeScript/TSX in the same repo, with working
  `impact` on symbols from both. It does not publish a supported-language list, so
  setup still measures per-repo and records `Graph support`.
- **Cost:** ~62s for 4,200 nodes / 11,200 edges. Files over 512KB are skipped
  (raise with `GITNEXUS_MAX_FILE_SIZE=<KB>`).
- **Pin a version** once one works for you — `npx gitnexus` fetches the newest each
  time, so teammates can otherwise index with different behaviour.
